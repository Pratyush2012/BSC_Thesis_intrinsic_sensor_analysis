\chapter{Experimental Setup}
\label{ch:setup}

\section{Robot Platform}

The experiments were conducted on \emph{Ricbot} (\Cref{fig:ricbot}), a compact wheeled platform developed at DTU for the Robotic Intercropping project~\cite{RoboticIntercroppingDTU2026}. Ricbot is designed for rapid field deployment: the chassis can be partially disassembled to fit within a $55\,\text{cm}$ vertical envelope so that it can be transported in a standard vehicle and carried by one or two people, with a total mass of approximately $25$--$30\,\text{kg}$~\cite{RicbotWiki}.

The drivetrain reuses the motors and wheels of the older \emph{Elektor Wheelie} platform, giving Ricbot a two-wheeled differential-drive configuration with passive support casters. The on-board computer is a Raspberry Pi running ROS\,2, with a Teensy~4.1 microcontroller handling low-level encoder and motor I/O (\Cref{fig:ricbot_back}). Sensor messages are bridged from MQTT into the ROS\,2 graph and synchronised across nodes via PTP (Precision Time Protocol), and all sensor streams are written to timestamped plain-text log files on the on-board computer, one file per sensor per run.

\section{Sensor Suite}

Two sensor modalities were used in this study; both are intrinsic to the robot and require no external infrastructure.

\subsection{Accelerometer and Gyroscope (IMU)}

A six-axis MEMS IMU of the InvenSense \texttt{MPU-9250} family is rigidly mounted to the robot chassis (\Cref{fig:ricbot_imu_closeup}) and provides linear accelerations and angular rates. The \texttt{MPU-9250} integrates a three-axis accelerometer, gyroscope and magnetometer on a single die; only the accelerometer and gyroscope channels are used here, as the magnetometer is heavily disturbed by the robot's own motors and electronics. Accelerations are recorded in units of $g$ (the gravity axis reads approximately $-1\,g$ at rest) and angular rates in degrees per second.

The IMU is driven from the Teensy~4.1 firmware via the \texttt{MPU9250\_asukiaaa} Arduino library, which initialises the accelerometer to $\pm 4\,g$ (sensitivity $8192\,\text{LSB}/g$) and the gyroscope to $\pm 1000\,^{\circ}/\text{s}$ (sensitivity $32.8\,\text{LSB}/(^{\circ}/\text{s})$). The library does not write to the on-chip Digital Low-Pass Filter (DLPF) registers, so the sensor runs at its power-on defaults bandwidths: $460\,\text{Hz}$ for accelerometer (internal sample rate $1\,\text{kHz}$) and $250\,\text{Hz}$ for gyroscope (internal sample rate $8\,\text{kHz}$). No firmware-level gyro bias correction is applied (\texttt{gyro\_offset = 0\,0\,0} in \texttt{robot.ini}). The Teensy forwards each new IMU reading to the Raspberry~Pi as it becomes available; across all data-collection runs the log streams have a consistent median inter-sample interval of $\approx 12\,\text{ms}$ ($\approx 83\,\text{Hz}$) for both channels.

The physical axis convention used throughout this thesis, verified empirically from rest-period accelerometer biases in the raw logs, is:
\begin{itemize}
    \item \textbf{Accelerometer:} $a_x$ - lateral (left/right), $a_y$ - vertical (gravity axis, $a_y \approx -1\,g$ at  rest), $a_z$ - longitudinal (front/back).
    \item \textbf{Gyroscope:} $g_x$ - pitch rate, $g_z$ - roll rate. The yaw rate $g_y$ is \emph{excluded} because it encodes intentional turning commands rather than terrain-induced motion.
\end{itemize}

Each log line stores four whitespace-separated columns: the Unix timestamp in seconds and the three sensor components $(a_x,a_y,a_z)$ or $(g_x,g_y,g_z)$. Comment lines prefixed with \texttt{\%} describe the file type and layout, and are skipped during parsing (see \Cref{lst:acc_header}). The \texttt{IMU1} tag reflects a logging schema that supports several IMUs in principle, although only one was active in this study.

\begin{lstlisting}[language=, caption={Header of a raw accelerometer log.}, label={lst:acc_header}]
% Accelerometer logfile (IMU1)
% 1   Time (sec)
% 2-4 Accelerometer (x,y,z)
1771853111.8137  0.0624 -1.0024  0.0056
1771853111.8258  0.0562 -1.0027  0.0065
\end{lstlisting}


\subsection{Wheel Odometry}

Wheel-encoder velocities are read by the Teensy microcontroller and forwarded to the Raspberry~Pi each time a new estimate is available. The median inter-sample interval differs between the two collection campaigns: $\approx 130\,\text{Hz}$ ($7.7\,\text{ms}$) on the campus runs and $\approx 83\,\text{Hz}$ ($12\,\text{ms}$) on the farm runs, likely due to the higher system load from the additional modules (cameras, GNSS) connected during the farm campaign. Each log line contains the timestamp, the left and right-motor velocities $(v_1, v_2)$ in $\text{m}/\text{s}$, and two integer debug counters that are discarded during preprocessing. The forward speed is derived as $\bar v = (v_1 + v_2)/2$, and all sensor streams are subsequently resampled onto a common $100\,\text{Hz}$ grid (\Cref{ch:processing}), so the per-campaign rate difference is absorbed before feature extraction. Downstream, wheel odometry contributes to features through speed-normalised statistics of the IMU signals and is used to partition the feature table into two speed-regime sub-datasets (\Cref{ch:feature}).

\section{Data Acquisition Setup}

All sensor streams are recorded simultaneously on the on-board Raspberry~Pi. A run begins when the robot is powered on and the logging service starts, and ends when the robot is powered off, or manually cut-off; each run produces a directory named \texttt{log\_YYYYMMDD\_HHMMSS.xxx}, where the suffix encodes the logger start time to millisecond resolution and all log files share a common run-relative timeline. A typical run directory layout is shown
in \Cref{lst:run_dir}.

\begin{lstlisting}[language=, caption={Layout of one raw run directory.}, label={lst:run_dir}]
log_20260421_113423.000/
|-- log_t0_acc_1.txt            % Accelerometer (IMU1)
|-- log_t0_gyro_1.txt           % Gyroscope     (IMU1)
|-- log_t0_encoder_velocity.txt % Odometry
|-- labels_config.json          % Terrain time ranges (post-hoc)
|-- metadata.md                 % Date, location, weather notes (post-hoc)
\end{lstlisting}

All timestamps are absolute Unix epoch seconds with sub-millisecond resolution, allowing the multi-sensor streams to be aligned onto a common $100\,\text{Hz}$ grid in postprocessing (\Cref{ch:processing}). Because each sensor is sampled by an independent firmware loop, the raw streams exhibit small per-sample jitter: the instantaneous sampling period was within $\pm 1\,\text{ms}$ of the median in 99\% of samples, with a worst-case observed value of $29.2\,\text{ms}$ on the accelerometer (a $\sim 2.4\times$ excursion from the nominal $12\,\text{ms}$). These rare gaps are detected and handled in the segmentation step (\Cref{ch:processing}).

No external sensors (camera, LiDAR, GNSS, motion capture) feed the classification pipeline; the only non-intrinsic input is a hand-held video used for post-hoc labelling of terrain segments (\Cref{ch:collection}).
